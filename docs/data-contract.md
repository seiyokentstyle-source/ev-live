# データの契約

`data/machines/**/*.json` は外部リポジトリ **`777site-scraper`** の
`make_evlive_data.py` が生成する。サイトはこれを読むだけで、書き換えない。
この文書は「生成側が満たすべき形」をサイト側から示したもの。

## 置き場

```
data/machines/*.json              既定店舗（新宿）
data/machines/<店舗id>/*.json     他店。店舗idは site/lib/halls.ts と揃える
```

店舗idは生成側の `halls.py` の「データ小分け」と同じ値にすること。
ズレると、サイトには店舗が出るのにデータが無い状態になり、しかも黙って
空表示になるので気づきにくい。

## 各JSONが満たすこと

- `site/lib/ev/validate.ts` の `validateMachine` を通る形であること
- `baseAnchors` の各要素は `{ g, ev, rtp, n? }`

| キー | 意味 |
|---|---|
| `g` | 現在G（AT間機種は AT・RB 間のハマりG） |
| `ev` | 期待値（円） |
| `rtp` | 1枚20円基準の換算機械割（%）。**不変条件 `(rtp >= 100) == (ev >= 0)` を必ず維持する** |
| `n` | そのGの推定に使ったサンプル数（任意） |
| `playG` | 1セッションの平均消化G（通常時＋AT中）。機械割と時給に共通の分母 |

`rtp` と `ev` の符号がねじれると、表で「機械割100%超なのに期待値マイナス」という
あり得ない行が出る。生成側で丸めた結果ねじれることがあるので、そこは寄せてから出す。

期待値表の表示はレートを問わず `100 + ev / (20 × bet × playG) × 100` で計算する。
`bet` は `evCalc.bet`、未設定なら3枚。46/52の `ev` は貸単価と換金単価の差を
引いた現金収支なので、列名は「換算機械割」とする。3枚掛け・800G/時なら
1ポイントが時給480円に対応する。公表設定別機械割・設定1の獲得補正の目標値・
設定狙いの実測OUT/INはこの換算の対象ではない。

サイトは補間・条件補正後のEVと、時給計算と同じ消化Gから機械割を再計算する。
旧JSONの `rtp` を使った表示や、機械割同士の線形補間は行わない。
`playG` のない旧プロファイルは、時給と同じく天井までの残りGで近似する。
消化Gが0なら時給0円・機械割100%とする。表示は小数1桁で、損失側の値が
100.0%に丸まる場合は99.9%とするため、表示値から時給を戻すと丸め差が生じる。
データファイル全体の読込時に変換せず、表示する行だけを計算する。
公開JSONの旧 `rtp` は生成側の次回更新まで残るが、画面は常に上記の換算式を使う。

## 低設定想定店舗混合の表

現在の対象はヴヴヴ2・マギレコ・SAOIIの3機種。生成側は任意の
`setting1Correction` に `schemaVersion: 1`、`sourceHallId: "shinjuku"`、
`targetRtp`（0〜1の比率）、`payoutScale`（正の倍率）、`method`、`profiles` を出力する。
補正後の `profiles` は新宿側の非「設定1想定」profileと同じキー・順序・狙い方・
レート・絞り込み・G列・母数を持つ。元の実測profileは別途そのまま保持する。

`method: "payout-scale"` は機種全体の実測投資G・回収から設定1の機械割に合う
獲得倍率を求め、全条件へ適用する。投資と条件判定に使う実測値は保持し、回収と
AT消化Gから期待値・機械割・時給を再計算する。条件ごとの機械割を一律に設定1へ
揃える処理ではない。SAOIIのように設定1から獲得を逆算済みの場合は
`method: "assumed-payout"`、`payoutScale: 1` とし、二重補正しない。

サイトは混合店舗に補正済みprofileを選択し、獲得倍率を重ねて補正しない。
機械割表示には上記の共通換算式を使う。新宿には元の実測profileを表示する。
補正対象の設定狙い・AT獲得分布などは混合店舗に転載しない。
公開する店舗別データから `setting1Correction` 自体を除き、二組の表を重複配信しない。
bundleのない旧データは従来の選択処理を使う。

稼働中の旧収集処理がrootのJSONを更新しても補正表を失わないよう、混合店舗用の
確定済み表を `data/machines/mixed/` に保存できる。rootに同じ日付以降の有効な
`setting1Correction` があればそちらを優先する。rootに補正がない場合や補正の対象日が
古い場合は混合店舗用の表を使い、各表自身の対象日・母数を表示する。補正していない
新しい実測値へ、古い補正倍率をサイト側で掛けることはしない。

## 収集済みだが期待値を算出できない機種

通常時・AT・獲得枚数とカウンター信号の対応を確認できない場合、保存済みの行を
EVサンプルとして数えない。`meta.samples` は `"0"`、各プロファイルは
`dataPending: true`、`baseAnchors: []` とし、`pendingReason` に確認待ちの理由を書く。
算出していないEV・出玉・設定推定・理論値・保存対象の数値は生成しない。

保存済み件数は任意の `meta.collection` に分ける。`rows` は状態行を含む保存行数、
`events` はBB/RB/ART等の信号件数、`units` は台数、`days` は日数。
`firstDate` / `lastDate` は保存データの対象期間（YYYY-MM-DD）を示す。
信号件数は実際のAT・ボーナス回数と同一とは限らない。

サイトは `meta.collection` がありEVサンプルが0件の間、「収集済み N行 / 期待値算出保留」
として掲載し、公表仕様・収集状況・保留理由を表示する。`pendingReason` がない既存の
`dataPending` プロファイルには、従来の実戦データ未収集メッセージを使う。

### 公表設定1による暫定参考表

確認済みの公表入力と明示した仮定から別途生成する場合に限り、任意の
`provisionalSetting1` を付けられる。これは実戦EVの算出保留を解除しない。
`meta.samples: "0"`、`profiles[].dataPending: true`、空の `baseAnchors`、収集件数と
保留理由を保持する。既存の `theoretical` や `setting1Correction` へ入れない。

契約は `schemaVersion: 1`、`status: "provisional"`、`model: "capped-geometric-v1"`、
`graphCorrected: false`、`historyBased: false`。`label` は
「公表設定1を仮定した暫定・グラフ未補正の参考表」とし、`note`、6項目以上の
`assumptions`、HTTPSの出典 `sources: [{ label, url }]` を必須にする。

`publicInputs` は `firstHitMeanGames`（通常時平均待ちGと仮定した公表分母）、
`setting1Rtp`（0〜1）、`medalsPerGame`、`bonusNetMedalsPerGame`、
`nominalCeilingGames`。`modelInputs` は `bet: 3`、`normalHitProbability`、
`assumedFixedPayout`。通常時は一定確率・公称天井で強制当選と仮定し、天井込み平均を
公表分母に一致させる。純獲得は一定と仮定して0Gからの等価出率から逆算する。
実測の当選分布・平均獲得を意味しない。天井の+α等の省略によって、特に天井直前の
参考EVが上振れしうる。G軸と店舗の外部カウンターの対応も未確認として表示する。

`rates` は46/52・50/50の順に2表を持ち、各表は `key`、`label`、`loanPerMedal`、
`creditPerMedal`、`anchors`。各行は `{ g, ev, rtp, inv, playG }` のみで、0Gから
公称天井未満の10G刻み。`n`・実測サンプル数などは含めない。サイトは入力から
係数・行を再計算して検証し、保留中の実戦値と別の表で表示する。推奨ボーダーや
実測の色分けは付けず、列名は「収支換算率」。既存と同じ現金収支式を丸め前の収支へ
適用した生成値を検証して表示する。46/52の換算率を公表機械割とは呼ばない。

公開対象は生成側が検証・登録した `data/provisional-setting1.json` に限定する。
共通カタログの形は `{ schemaVersion: 1, machines: [{ id, name, reference }] }`。
`reference` は上記の完全な参考表で、機種ID・正式名の重複や不正な表を許可しない。
サイトはこのカタログをビルドへ含め、ライブ取得した参考表も登録済みの機種ID・正式名・
公表入力と照合する。ライブ側の自己申告入力だけでは機種を追加できず、別機種への
付け替えも受け入れない。追加対象の公表入力を登録すれば、機種別UIの追加は不要。

同じ店舗に保存済み履歴があり、実測サンプル0件・全プロファイル算出保留の機種には、
機種JSONに参考表がなくても共通カタログから補完する。実戦値や検証済みの
`counterEstimate` が利用可能ならそちらを優先する。機種JSONがまだない収集状況だけの
機種にも、登録された機種IDと正式名が一致すれば `LiveCollection.provisionalSetting1`
として渡す。`forcePending` は解除せず、保留された数値プロファイルは公開しない。
未収集店舗・保存行0件・機種不一致・未登録機種へ自動的な参考表を出すことはない。
収集件数・対象日・保留理由・既存JSONは変更せず、収集状況DTOや一覧の母数へ参考値を
混ぜない。共通カタログは他店舗の実測値を含まない。一覧・詳細・ライブ更新は同じ
選択規則を通り、参照表の変更もライブ更新のrevisionに含める。

### スルー回数別の穢れ解放率（throughRelease）

2026-09-29 利用者指定。対応機種（現在は東京喰種）だけ任意の `throughRelease` を付ける。
`{ label, note, rows }` で、`rows` は `{ through, label, n, hits, rate }` を0回から連続で並べ、
最後の行は「16回以上」のようなまとめ行。`rate` は `hits / n`（小数4桁）、`n=0` の行は `null`。
スルー回数＝当日0から、当選に繋がらなかったCZと単発ATの合計（2連以上のAT終了で0に戻す）。
穢れ解放＝次のATが2連以上かつ1本目の獲得70枚以下。サイトは「穢れ解放」モードで表示する。
同じスルー回数は期待値表の絞り込み軸 `s`（evFilters）と、狙い目の条件 `through_since_chain` でも選べる。

### リコリス・リコイルの通常形式の推定表

2026-10-06 利用者指定。リコリスは新宿東宝と同じ信号・獲得推定モデルを、歌舞伎と
店舗混合のそれぞれの履歴にも適用する。通常の `profiles` に朝一・駆け抜け後・それ以外を
46/52・50/50で生成する。元の獲得枚数は実測ではなく、補正前は平均設定2.3を仮定した推定。
店舗間で新宿の計算済み表を流用しない。`meta.samples` と各profileの母数はその店舗の
集計値とし、通常表ができた機種へ旧 `counterEstimate` / `provisionalSetting1` を併記しない。

店舗混合JSONの `profiles` は補正前の推定表で、`mixed-raw` で表示する。
`setting1Correction` は同じセッションへ共通の獲得倍率を適用した設定1・97.9%の補正表で、
`mixed` で表示する。初当たり分布・母数・通常時投資を変えず、サイトで追加補正しない。
どちらも獲得が推定であることをラベル・算出条件に残す。

### 旧形式のカウンター履歴からの推定表（counterEstimate）

2026-09-28 利用者承認。同じ店舗の外部カウンター履歴（信号とG数）から生成側のプログラムが
計算した推定表を、任意の `counterEstimate` として付けられる。現在は `lycoris` の新宿だけ。
付く場合は `provisionalSetting1` の代わりで、両方は付かない。実戦EVの算出保留は解除しない
（`meta.samples: "0"`、`profiles[].dataPending: true`、空の `baseAnchors` を保持）。
他店の履歴から作った表を別の店舗に付けない。サイトも機種IDと店舗（`lycoris` は `shinjuku`）を照合し、
他店のフォルダや混合店舗（新宿の機種から作る表を含む）では推定表を取り除く。
収集状況ページ（`LiveCollection`）でも参考表との同時付加を拒否する。

契約は `schemaVersion: 1`、`status: "estimate"`、`model: "lycoris-counter-v1"`、
`historyBased: true`、`graphCorrected: false`、`label` は
「カウンター履歴から計算した推定期待値表（獲得枚数は推定）」。`note` と5項目以上の
`assumptions` を必須にする。`summary` は `unitDays`、`firstDate`、`lastDate`、
`excludedDates`、`assumedAverageSetting`、`assumedRtp`、`firstHitGames`、`meanPayout`、
`normalBonus`、`upperBonus`、`kakeShare`、`normalShare`、`upperShare`。
獲得枚数は履歴に無いため、仮定の平均設定の公表出玉率に合うよう逆算した推定値である。

`groups` は `all`・`after_kake`・`after_normal`・`after_upper`（前回ATの種類）の順。
各グループは46/52・50/50の順に `rates` を持ち、各行は `{ g, n, ev, rtp, inv, playG }`。
`g` は0Gから10G刻みの連続、`n` はその打ち始めGでの件数で、行が進むほど増えない。
件数が足りない打ち始めGは生成側が出さない（`all` 以外は空でもよい）。G軸は店舗の
外部カウンターから推定した通常時Gで、液晶Gとは一致しないことがある。サイトは形と
来歴を検証する（数値の再計算は履歴を持つ生成側の `lycoris_counter_ev.validate_counter_estimate`）。

### 機種JSONと独立した収集状況

未確認スペック・サンプル不足・収集未完などで機種JSONを生成できない場合は、
生成側の `data/halls/<hallId>/collection-status.json` を補助情報として使う。
形式は `evlive-collection-status/v1`。検証済みの保存データがある機種について、
同じ機種ID・名称・別名・店舗識別、観測した `collection` の件数と期間、
`pendingReason`・`reasonCode`・`collectionComplete`・`forcePending`、
生成元を照合する `sourceIntegrity` を保持する。履歴0行でも台の日次情報を保存済みなら
`rows/events: 0` と台数・日数を持てる。`expectedUnits` は確認済みの場合だけ正整数で付ける。

取得元は `daidata` または `site_seven`。`storeId` は登録済みの識別値で、Daidataは6桁の
`store_id`、Site Sevenは4〜16桁の `hall_code` を使う。未知の機種は取得元の完全名を保持し、
メーカーは「未確認」、導入日は `releaseDate: null` とする。部分一致で別機種の仕様を借りず、
発売日・獲得枚数・期待値の仮値を入れない。導入日未確認でも検索・一覧・店舗別の保留画面に掲載する。
数値機種JSONの導入日を文字列で必須とする既存契約は変えない。

正式登録するときも最初の機種IDを引き継ぐ。旧メーカーが「未確認」かつ旧導入日がnullの場合のみ、
名称・メーカー・導入日・共通完全名の補完を許す。旧名・旧共通名を含む別名一覧は残し、
件数・観測期間を減らさない。正式登録済みの識別情報をこの例外で書き換えることはできない。
カタログを更新しない数値表の追加・更新にも同じIDの条件を適用する。同店舗のカタログの
完全名または共通完全名が、数値機種の名称・別名と完全一致した場合はID一致を必須とする。
別店舗のカタログや略称同士の一致では結び付けず、シリーズ機種を混同しない。

通常のカタログ項目は表示の補完に限定し、利用可能な店舗別の機種JSONを常に優先する。
明示的に確認待ちとした `forcePending: true` の項目だけは数値表示を保留にする。
元の機種JSONは変更せず、新規数値表の最低サンプル条件や生成時の採用判定にも使わない。
数値表を生成できるようになった後も収集記録は残す。データguardは機種・店舗の取り違え、
保存件数・期間の退行と項目削除を拒否する。

補完表示には `evlive-live-collection/v1` という専用の静的配信形式を使う。
公開するのは機種の識別情報、保存件数・実際の観測期間、保留理由だけで、
EVプロファイル・設定狙い・獲得枚数・交換条件・計算用スペック・保存狙い目は含めない。
ブラウザも専用画面で表示し、金額計算を実行しない。未確認スペックを表示用の仮値で埋めない。

機種一覧は公開対象の全店舗を統合し、同じIDのカードは新宿を優先して1枚にする。
件数は合算せず、採用した店舗名をカードに添える。静的HTMLとライブ更新で同じ規則を使い、
未登録・準備中の店舗は一覧の件数ソースにしない。

## 巻き戻さないこと

期待値データは毎晩の収集で前へ進むだけの資産で、後ろへは動かない。
古い土台で再生成したJSONを新しい `main` へマージすると1日ぶんが黙って消えるため、
`data-guard` workflow が PR と `main` への push で止める。
詳しくは [CLAUDE.md の「データは巻き戻さない」](../CLAUDE.md) を参照。

### 生成日を誤記した旧データの互換比較

`lastUpdated` はデータ対象末日を表す。旧生成器の全体再生成
`fc18d936f2d3f4b6449f6a0bef474db9fb2249fd` は実行日2026-09-13を誤記したが、
その58機種の `meta.source` に記録された対象期間末日は2026-09-05だった。
生成器は修正済みで、後続の機種別更新は対象末日を出力する。

guardはこの旧出力だけを読み取り時に互換比較する。
`scripts/legacy-data-dates.json` に元コミットと58個の完全JSONのSHA-256を固定し、
ファイルパス・解析後のJSON内容・旧 `lastUpdated`・既定書式の対象末日が全て一致する場合のみ、
2026-09-05を比較日とする。空白や改行は無視するが、非公開データを含め値の変更は許さない。
任意の `meta.source` だけを根拠に更新日を下げることはできない。

この旧出力から生の更新日が下がる移行では、後続JSONにも
`実戦データ自動収集（YYYY-MM-DD〜YYYY-MM-DD・全データ）` の有効な期間が必要で、
期間末日と `lastUpdated` が一致し、2026-09-05以降でなければならない。
既定書式以外、壊れた日付、末日の不一致、ハッシュ不一致の旧出力は自動移行しない。
旧出力をHEADへ戻す場合にも同じ比較日を使い、例えば9/07から9/05への後退を検知する。
生成JSONや表示日付は書き換えない。

件数の減少・機種JSONの削除は従来通り独立して検査する。比較元のコミット・JSONが
取得できない、BASEまたは作業ツリーのJSONや更新日が不正、既存件数が欠落・不正な場合は、
`[allow-data-regression]` があっても確認不能として停止する。

`schedule`＋`workflow_dispatch` のジョブを置いて同じことをさせる想定。

## 公開画面のサンプル更新

ビルド時に `/live-data/index.json` と `/live-data/<店舗id>/<機種id>.json` を静的出力する。
一覧は機種の表示用情報と更新判定用の `revision`、詳細は検証済みの `machine` と
掲載中の `savedTargets` を持つ。`intervalExplorer` や掲載対象外の狙い目は含めない。
`revision` は公開する内容全体のSHA-256とし、同じ更新日内のサンプル増加・再計算も検知する。

画面表示中は60秒ごと、および画面に戻ったときに一覧を取得し、変更のあった機種の詳細だけを
取得する。選択中の狙い方・レート・利用可能な絞り込みは保持する。通信失敗や一覧と詳細の
版が揃わない場合は表示中のデータを保持し、次回に再試行する。

## ヴァルヴレイヴ2のCZ間の表示

通常のCZ間は「0スルー」と「1スルー以降」に分けて表示する。
公開境界の `splitCzThroughProfiles` が、既存の `cz` 軸の集計行を条件別に分け、
通常の絞り込みと同じ合計から期待値・消化G・機械割を求める。
0スルーは72Gから、1スルー以降はCZ後0Gからとし、G数の原点は移動しない。
1スルー以降では個別回数と他の軸の掛け合わせを引き続き使える。

対象は `vvv2` の `cz_ceiling_4652` / `cz_ceiling_5050` と、その設定1補正。
通常表を `cz_ceiling_zero_*` / `cz_ceiling_after_*` に置き換える。
リセット・引き戻し・探索用モデルの条件と数値は変更しない。
元の全区間数・平均初当りG・総獲得は分割集計から復元できないため引き継がず、
各G行のサンプル数を表示する。表示上限は元の通常表を超えない。

ページ・ライブ更新と集計アセットの書き出しには同じ変換を適用する。
収集側の機種JSONは変更せず、次回の収集後も同じ分離を行う。
分割軸を持たない旧形式は、別の集団を推測で作らず従来の表を維持する。

## 手動で掲載する狙い目

### 通常表の狙い方と絞り込み

`profiles[].aimKind` は任意で `cz` / `bonus` / `at_non_runthrough` /
`at_runthrough` を取り、この順に表示する。名称と天井は生成側の `label` / `ceiling`
を使う。旧表に分類を推測して付けず、AT全体を駆け抜け後以外と言い換えない。
駆け抜け後に短縮天井がある狙い方は、絞り込み軸の採否とは独立して保持する。

`evFilters.axes` は機種・狙い方ごとに採用した軸の順序・表示名・選択肢。
明示的な空配列は「軸なし」を表し、旧 `tails` / `days` / `cz` へ戻らない。

海門決戦（`mcd43a818`）の上位後には、利用者指定の次の3軸を生成側が宣言する。
これらは通常の軸選別で落とさず、上位以外の狙い方へは持ち越さない。

- `kaimon_count`: 直前の連チャン区間内の6〜8G ART信号を海門回想として数えた回数。
- `kaimon_since_pay`: その区間の最後の海門回想信号の次の履歴から、区間終了までの観測獲得合計。
  回想信号自身の獲得は含めない。回想が無ければ不明で、0枚を補わない。
- `kaimon_day_seen`: 直前連チャンの推定区間差枚が2,000枚以上の場合、当日の打ち始めまでに
  海門回想信号が無ければ0、あれば1。区間内の通常時消費を控除し、初当たり前の投資は含めない。
  2,000枚未満や差枚不明は対象外とし、指定なしでは保持する。

サイトは宣言された選択肢で完全一致の集計セルを掛け合わせる。台・日・個別信号の履歴は
公開集計に含めない。探索用の暗号化データでは同じキーを `normalAxes` / `normalValues` に持ち、
上位後の `profileKeys` / `sourceProfileKeys` に限定して、比較・探索・保存・再集計に使う。
分類付き、または `selectionPolicy` を持つ表は初期値をすべて「不問」と表示し、
本表はその全不問の集計を持つ。旧データの既定CZ条件などは改名だけで変えない。

`evFilters.selectionPolicy` は生成側の採用方針を示す任意オブジェクト。
1G開始・同じ交換条件と他条件に固定し、対象軸の指定と不問の機械割に
上下どちらも1ポイント以上の差があれば採用する。単独で差がなくても
かけあわせで差が出る軸を保持する。周辺G帯や別期間での確認は採用条件にしない。
この選別は通常表専用で、暗号化された探索用データの軸・少数サンプルには適用しない。

表キーは軸の宣言順に `key + value` を連結する。選択値が宣言済みで、キーが
一意な条件へ解釈できることを検証する。複数条件は完全一致する `tables[key]` だけを
表示し、別の表の加算・代用をしない。単独表のない軸も選択可能で、途中の組合せに
集計がなければ結果なしを表示して、次の軸を指定できるようにする。

`evFilters.aggregation` があれば従来の `tables` より優先する。
ただし `heaven_` の固定帯は既存の `tables[key]` を保持し、各軸を単一選択とする。
他の狙い方から複数値を引き継いだ軸は不問に戻し、複数値指定の合算で代用しない。
`heaven_` の持ちメダル調整には、帯ごとの任意マップ `evFilters.tableAggregations` を使う。
キーは既存の `tables` と対応し、各値はv2・`axisKeys: []` の独立集計とする。
行は `[g, n, sumNormalGames, sumPayoutMedals]` で、その帯に採用された件数と収支を再現する。
不問用の `aggregation` から帯を切り出して代用せず、専用集計がなければ再集計待ちにする。
0枚では元の固定表を使う。帯別集計も以下と同じ圧縮・asset分離・検証経路を通す。
形式は `{ schema: "evlive-filter-aggregates/v1" | "evlive-filter-aggregates/v2", axisKeys, rows, costPerGame,
exchange, medalsPerGame, junzou, bet, investmentMinimum, minPlay?, roundingEpsilon }`。
`axisKeys` は `axes` と同じキー・順序で、
各行は `[g, ...optionIndexes, n, sumNormalGames, sumPayoutMedals]`。
選択肢は0始まりの添字、`-1` は不明・範囲外で、不問時には含め指定時には一致しない。
任意の `axisMatchModes` は軸と同じ長さの `"single" | "bitmask"` 配列で、省略時は全軸single。
bitmaskの軸値は選択肢indexに対応するビット集合で、1軸30選択肢までとする。
指定時は対象ビットが立つセルを含め、未知を表す `-1` は一致させない。
例えば13日の「特定日」は「1のつく日」「3のつく日」の両ビットを同じ行に持つ。
行を複製しないため、不問や他軸だけの指定では13日の件数を二重計上しない。
台番号・日時・履歴ID・イベントは配信しない。v1は同じG・軸値のセルが一意で、
軸値が一致するセルの件数・投入G・獲得を合算してから平均を計算する。
v2も行の幅は同じだが、1行内の通常投入Gは全件同じとする。
`n` は正の整数で、`[g, ...optionIndexes, sumNormalGames / n]` が一意になるよう集約する。
この契約は生成側・通常行の検証・圧縮展開後の検証で共通とする。

現金収支合計は `sumPayoutMedals * exchange - sumNormalGames * costPerGame`。
EVはその値を `n` で割り、平均消化Gは
`(sumNormalGames + sumPayoutMedals / junzou) / n`、平均投入は
`sumNormalGames * medalsPerGame / n`。純増0の場合はAT中Gを0とする。
換算機械割は合計収支を `20 * bet * 合計消化G` で割り100倍して100を加える。
セルごとの平均や機械割を単純平均しない。結果の実台数・実初当りGは
この合計から求まらないため表示しない。少数サンプルの下限を設けず、
1アンカーも表示できる。0件のGは表示せず、全不問時は既存の本表をそのまま使う。
合算後の投資が `investmentMinimum: "mean"` なら1件平均で1円以上、`"total"`
なら合計1円以上のGだけを表示する。`minPlay` があれば平均通常時Gがその値以上であることも必要。
EVの円丸めは生成側の `round_ev` と同じ半偶数丸めで、半円境界の誤差は
`roundingEpsilon`（標準 `1e-8`、0以上0.25未満）まで正規化する。

持ちメダルは0以上の安全な整数で入力し、交換差がある場合はv2を必須とする。
各行の使用量合計を `n * min(持ち枚数, sumNormalGames / n * medalsPerGame)` とし、
その合計に `costPerGame / medalsPerGame - exchange` を掛けた額を現金収支合計へ加える。
持ち枚数自体は獲得に加えず、平均投資へ先に `min` を適用する近似もしない。
調整後の合計を平均してから円丸めを1回行い、表示EVから時給・換算機械割を更新する。
0枚と等価交換では既存値を維持する。不問と `heaven_` の固定帯は同GのEVだけを更新し、
元表のG列・範囲・件数・投入枚数・消化G・その他のメタデータを変えない。
元表のGに対応する集計が欠ける場合は代用しない。v1など未対応の表は再集計待ちを表示する。
保存狙い目・全体平均の理論表・暫定表には、この入力を適用したと表示しない。

行数が多い集計は `rows` の代わりに `rowsGzip`（行配列JSONをgzipしbase64化した文字列）と
`rowCount`（展開後の行数）を持つ。両形式の併記は禁止。gzipは生成側で `mtime=0` として
同じ内容が同じ出力になるようにする。収集側の機種JSONはこの形式を維持する。
公開ビルドは行payloadを `/filter-aggregates/<sha256>.json` へ分離し、初期HTML・RSC・
ライブ配信では `rows` / `rowsGzip` の代わりに `rowsAsset: { sha256, rowCount }` を渡す。
軸・財務定数は元のプロファイルに残す。asset本文は `{ rows }` または
`{ rowsGzip, rowCount }` だけで、配信するUTF-8 JSON全体のSHA-256を名前に使う。
同じ行payloadは店舗・交換率をまたいでファイルを共用できるが、計算時の財務定数は共用しない。
ブラウザで選択中の狙い方に絞り込み、または交換差のある持ちメダルを指定したときだけ、
basePath付きの固定内部URLから取得し、SHA-256・envelope・件数を確認して展開する。
不問で持ちメダルの調整も不要なら取得しない。
更新日の変わらない再計算も参照hashとライブrevisionが変わるため、新しい行へ切り替わる。
旧版assetの404も読込失敗として扱い、新版のライブ更新を受けた時点で新しい参照を使う。
展開後に行数・軸添字・数値・セルの一意性を通常形式と同じ契約で検証する。
計算中・読込失敗は明示し、指定条件の結果として不問の値を代用しない。
機種・狙い方・データ版が変わった場合は古い結果を画面に適用せず、展開キャッシュは直近2件まで。

掲載中の保存狙い目は通常の「狙い方」欄からも選択できる。集計行を通常プロファイルへ
変換せず既存の保存狙い目表示を使い、固定交換率・開始条件・空の最新集計を維持する。
従来の「狙い目」モードと `?target=<id>` リンクも引き続き利用できる。

`data/saved-targets/targets.json` が掲載対象・名称の正本。狙い目探しツールで利用者が
追加・取り外しを選んだときに更新し、私用の保存一覧とは分ける。全条件を公開しない。
カタログは `{ schema: "evlive-saved-targets/v1", updatedAt, targets: [...] }`。

各項目は `id`（UUID）、自由入力の `name`、`machineId`、`hallId`、`conditionKey`、
`publicationKey`、`definition`、`machine`、`profile`、`conditions`、`stopping`、
`rate: "46/52" | "50/50"`、`dataThrough`、`sourceRevision`、`updatedAt`、`rows` を持つ。
`conditions` と `stopping` は表示用の文字列。`assumedPayout?: boolean` は想定出玉の注記。
`conditionKey` は正規化した条件定義のSHA-256、`publicationKey` は公開するID・名称・
条件定義のSHA-256。更新日付は `YYYY-MM-DD`、版は64文字の小文字16進数。

`definition` は `schema: "interval-target/v1"`、機種・店舗、`profileKey`、`startG`、
`endG`（未指定はnull）、`filters`、`rate: "46/52" | "50/50"`、`stopRule: "evlive"`。
フィルターは軸キーごとの `{ mode: "all" | "range" | "missing", lo, hi }`。
上下限は数値文字列／空文字列で、`hi` は排他的上限。空のrangeは「記録あり」を意味し、
allやmissingとは異なる。現在の店舗は新宿（`shinjuku`）。

公開する集計行は `{ g, ev, n, days, inv?, playG? }`。`ev` は期待値（円）またはnull、
`n` は該当区間数、`days` は収集日数。開始Gの昇順・重複なしで、終了G未満の行を持つ。
`inv` はその狙い目に該当する区間の平均投入枚数、`playG` は同じ区間の平均消化G
（通常時＋AT中）。いずれも有限の非負数またはnullで、サンプル0件の行ではnullとする。
生履歴や個別区間を追加せず、この2つの集計値だけを公開の許可項目へ追加する。

「狙い目」は「期待値稼働」と同じ6列（G数・機械割・期待値・時給・平均投入・
サンプル）で表示し、46/52の列名は「換算機械割」とする。
時給は `ev * gamesPerHour / playG`、換算機械割は上記の
1枚20円基準の式を使う。初期表示は10G間隔で、集計済みの行を表示間隔に応じて
絞り込む。行の補間は行わない。集計対象日は従来どおり狙い目の情報に表示する。

旧版の `{ g, ev, n, days }` 行も引き続き受け付ける。`inv` / `playG` が欠けるかnullの
指標は「—」とし、通常プロファイルや天井までの残りGから別の対象区間の値を補わない。
保存済み・再集計・ライブ更新・公開確認用JSONのすべてで、この後方互換の検証と
許可項目への絞り込みを通す。

収集側は機種JSONの任意フィールド `savedTargets` に
`{ id, conditionKey, sourceRevision, dataThrough, rows }[]` を出力できる。
サイトはカタログに載るIDと条件キーが一致し、集計日が古くない結果だけ採用する。
取り外したIDが機種JSONに残っていても表示しない。一致する更新がなければ、カタログの
追加時集計と日付を表示する。空の更新結果も有効で、古い非空の表へ戻さない。
旧収集コードの再集計行に `inv` / `playG` だけが欠ける場合は、カタログと
`sourceRevision`・`dataThrough`・条件キーが一致し、行の `g`・`ev`・`n`・`days` も
すべて一致するときだけ、カタログの集計値を補う。再集計側に値または明示的なnullが
ある場合はそちらを優先する。別の版・日付・集計結果や、空の更新結果には補わない。

ビルド時に `site/scripts/export-saved-targets.mjs` が検証・許可項目への絞り込みを行い、
公開状態確認用の `/ev-live/saved-targets.json` を出力する。生履歴・イベント・秘密鍵は
カタログや集計結果に含めない。公開リンクは
`/ev-live/machines/<machineId>/shinjuku/?target=<id>`。

## 店舗の台番号ヒートマップ

ビルドごとに、新宿の `getAvailableMachines()` が返す機種JSONの `settingAim` から
`evlive-floor-heatmap/v1` を直接生成する。旧 `data/halls/shinjuku-heatmap.json` は参照しない。
設定狙いと同じ、100G以上・最終AT終了即やめ想定の推定差枚を使う。
`groups` の `all` と `0`〜`9` の11群に台別 `{ unit, days, net }`
（有効日数・合計差枚）を持ち、表示は `net / days`。
欠測を0扱いせず、機種別の平均や回転数で加重もしない。

日付不問は既存の `settingAim.units[].net` と `days` を合算する。
特定日用に、同じ有効な `rates` の日を収集側で集計した任意フィールド
`dayDigitNets: { "0"?: { net, days }, ..., "9"?: { net, days } }` を追加する。
`net` は整数の合計差枚、`days` は正整数で、該当する有効日数と一致させる。
フィールドがある場合は有効日を持つ全数字を含め、該当日がない数字は入れない。
旧JSONにフィールドがない場合も日付不問は使えるが、特定日の差枚を期間合計から推測しない。
`rates` と `games` からの逆算や期間合計の比例配分もしない。

旧収集プロセスとの移行期間は、生成済みの設定狙いを保存した
`data/halls/shinjuku-setting-aim-compat.json`（`evlive-setting-aim-compat/v1`、
`machines: [{ id, available, settingAim }]`）を特定日の互換データに使える。
現在の台に `dayDigitNets` がない場合だけ、同一機種・台の保存済み有効日すべてで
日付・出率・回転数が現在も一致していることを確認して、その既知の内訳を利用する。
観測日数が同じなら合計差枚の一致も必要。新しい日が加わった場合も保存済みの日だけを使い、
特定日の対象期間・台日数はその保存済みの観測に限定する。
内訳が現在にあれば常にそちらを優先し、不正・不一致の保存値や別機種の値は補完に使わない。
日付不問は互換データで置き換えず、常に現在の `net` と `days` を使う。
互換データを利用した場合のみ `snapshotFallbackTo` にその観測の最終日を入れ、
特定日の注記に「一部の台でYYYY/MM/DDまでの集計済みデータ」を表示する。

機種入替で同じ台番号が別機種に現れる場合、日付が異なれば合算する。
同一台番号・同一営業日の重複は、差枚が同じでも自動採用せずビルド時にエラーにする。
期間合計しか持たない旧データの一部だけを差し引いて二重計上を解消したことにはしない。
ブラウザには各条件の集計値だけを渡し、日別履歴や計算コードを追加公開しない。

特定日は既存条件と同じ、サイトデータの日付数字を含む日（1なら1・10〜19・21・31日）。
対象期間・台日数は実データだけから算出する。生成時刻をデータ末日にはしない。
機種JSONが更新されるたび、同じビルドの設定狙いとヒートマップへ反映する。

表示先は `/ev-live/halls/shinjuku/heatmap/`。島図の664台は
`site/lib/heatmap/shinjuku-layout.ts` に位置だけを保持し、元画像の機種名・差枚色は再利用しない。
灰色は該当条件の履歴なし、0枚は中立色。色の閾値は日付条件を変えても固定する。

### 履歴あり・差枚未集計の台

機種JSONは金額を含まない任意フィールド `heatmapCoverage` を持てる。
形式は `{ schema: "heatmap-coverage/v1", reason, groups: { all: [...], "0": [...], ..., "9": [...] } }`。
11条件を必ず持ち、各行は `{ unit, days, firstDate, lastDate }` のみ。
台番号は先頭ゼロのない正の安全整数文字列、日数は重複営業日を除いた正整数、
期間は実在するISO日付で機種の `lastUpdated` を超えない。
特定日はゼロ埋めしない日にちの数字で抽出し、期間端点・日数はその条件の履歴に一致させる。

このフィールドは新宿の全機種から専用経路で読む。算出保留・非公開機種も履歴の存在だけ採用し、
金額は引き続き既存の `getAvailableMachines()` が返す設定狙いだけを使う。
同じ台・条件に差枚集計があれば差枚を優先し、履歴の日数を差枚の分母へ加えない。
差枚のない台は `groups[].pendingUnits` に理由・日数・期間を保持して紫の斜線で表示する。
灰色はその条件の履歴がない台、実際に算出した0枚は従来の中立色となる。
機種入替の期間が離れていれば履歴日数を合算し、重複する場合は `days: null` と
`overlappingPeriods` の期間別内訳で保持し、未確認の重複排除日数を表示しない。

旧収集プロセスの上書きや機種JSON未生成時には、生成済み
`data/halls/shinjuku-history-coverage.json` を履歴表示だけの補完に使える。
形式は `{ schema: "shinjuku-history-coverage/v1", hallId: "shinjuku", machines: [{ id, lastUpdated, coverage }] }`。
現行の機種JSONに `heatmapCoverage` があれば最優先する。
フィールドがなくても現行 `lastUpdated` が補完より古ければ採用しない。
機種JSONが未生成のIDは検証済みの補完をそのまま使えるが、金額データは復活させない。
欠落・不正な補完ファイルは利用せず、既存の差枚集計を維持する。
ヘッダーの期間は表示中の差枚・履歴双方を含み、差枚の集計期間メタデータ自体は変更しない。
